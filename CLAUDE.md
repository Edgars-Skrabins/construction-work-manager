# CLAUDE.md

## Project

Construction Work Manager is a work management module for construction sites. Admins manage employees, construction sites and work items. Managers assign work items at construction sites to their subordinate employees, limited by each employee's access level. Employees see the work assigned to them and where it has to be done. External pass systems call a versioned JSON API to find out which employees need access to a given construction site.

## Tech stack

- PHP 8.4 with Yii 3, one application built from the Yii 3 web template
- Microsoft SQL Server 2022 through `yiisoft/db-mssql` and `pdo_sqlsrv`
- Migrations with `yiisoft/db-migration`
- Authorization with `yiisoft/rbac` and `yiisoft/rbac-db`
- Twig views through `yiisoft/view-twig`, styled with Bootstrap 5 color modes: a dark and a light palette as Bootstrap variable overrides per `[data-bs-theme]` in `assets/main/site.css` (including the field border, focus and assignment status colours, `--app-status-*`, that `AssignmentDisplayStatus`'s badge and stripe classes use), plus the shared spacing and type scale variables in `:root`. The server renders `data-bs-theme="dark"`; `assets/main/theme.js` (`ThemeAsset`, loaded in `<head>` by `MainAsset`) switches it before the first paint to the choice stored in `localStorage` (`theme`) or else the system's `prefers-color-scheme`, and drives the navbar's theme toggle
- PHPUnit, PHPStan and PHP-CS-Fixer
- Docker Compose for local development, GitHub Actions for CI

## Layout

- `config/` holds the Yii configuration: `common/`, `web/` and `console/` DI definitions and parameters, plus per-environment parameters in `environments/`. Run `composer yii-config-rebuild` after adding or removing config files.
- `src/` holds the application code under the `App\` namespace. `src/Web/<Page>/` keeps a page's action and its Twig template together. `src/Web/Shared/Layout/Main/` holds the layout, its navbar partials (theme toggle, language selector) and the asset bundles (`MainAsset` depends on `SelectAsset`, so every page loads `assets/select/`), and `src/Web/Shared/Authentication/` the web login method. The other `src/Web/Shared/` folders hold what pages share: `Access/` (`RequirePermission`, `ViewAccess` and the `access-level-too-low-badge.twig` partial), `Caching/` (`NoStore`), `Calendar/` (`MonthCalendar`, `CalendarDay`, `CalendarEntry`, the `month-nav.twig` month and year selects, whose years come from `AssignmentRepositoryInterface::yearRange()` in the viewer's scope plus the current year ±1, and the `month.twig` grid partial shared by the Work calendar and My work calendar; `month.twig` registers `CalendarAsset`, whose `assets/calendar/calendar.js` truncates the entry cards, shows "+N more" and fills the details modal), `Listing/` (`ListParams` with `sort`, `page`, the search text `q` and the named positive-integer `filters` a list asks for, and the search-form, sort-link, pagination, row-actions, row-actions-sheet, truncated-text and empty-state partials; the search form registers `ListingAsset`, whose `assets/listing/instant-search.js` searches as you type, whose `row-actions.js` hides the Actions column below 1200 px (each row then ends in a chevron) and opens a row's actions in the row-actions sheet when the row is tapped, and whose `listing.css` holds the truncation widths and shows row actions only on row hover or focus where a mouse is used), `Modal/` (`ModalRedirect` and the `modal.twig` partial, which registers `ModalAsset` and its `assets/modal/modal.js`), `Form/` (field errors, `FormBody::string()` for reading posted fields, and the `date-input.twig` partial: a YYYY-MM-DD text field whose `DateInputAsset` adds a button opening the browser's date picker), `Flash/` (`FlashMessages`), `Language/` (the `Language` list, `LanguageMiddleware`, the `language` view parameter and the Twig `t()` function), `Redirect/` (`Redirector`), `Rendering/` (`RenderBeforeSessionClose`) and `Throttling/` (`TooManyAttempts`, the 429 response of a throttled form). `src/Entity/` holds plain entity classes, `src/Repository/` the repository interfaces and their `yiisoft/db` implementations, and `src/Service/` the services. `src/Environment.php` is the only place that reads environment variables. `src/Access/` holds the role permissions, and `src/Web/Forbidden/` holds the middleware that turns a `ForbiddenException` into the 403 page, and `src/Web/Language/` the action that switches the language. `src/Api/Shared/` holds the API pipeline (`ApiPipelineMiddleware`, `ApiErrorMiddleware`, `ApiKeyAuthentication`, `ApiNotFoundHandler`, `JsonResponseFactory`), and `src/Api/V1/<Endpoint>/` holds each API endpoint's action. `src/Console/` holds the console commands, registered in `config/console/commands.php`.
- `public/` is the web root, `assets/` holds the CSS and JavaScript published by the asset manager (asset bundles in `src/Web/Shared/Layout/Main/`; there is no inline JavaScript, because the CSP allows scripts only from `'self'`), `messages/<locale>/app.php` holds the UI translations, and `runtime/` holds caches and is not committed.
- `tests/Unit/` holds tests without a database. `tests/Integration/` holds tests that boot the real application in the `test` environment and extend `IntegrationTestCase`, which provides services from the app's container, `handleRequest()` to send a request through the app and `webMiddlewares()` to read the configured web middleware list. Test helpers shared by both suites live directly in `tests/`: `FixedClock` fixes the time for code that takes `ClockInterface`, `CallableRequestHandler` wraps a closure as a request handler, and `RecordingLogger` records log calls.
- `docker/` holds the Dockerfile, Caddyfile, PHP settings, the SQL Server init script and the dev environment file `dev.env`.
- `SQL/` holds the T-SQL scripts that define the schema and seed data, numbered in execution order.
- `docs/openapi.yaml` is the OpenAPI 3.1 description of the pass-system API. It's a repository file only; the app doesn't serve it.
- `specs/` holds the feature and fix specs.

## Architecture

- One application with two entry points: a server-rendered web UI for people (session login, HTML) and an API under `/api/v1` for external systems (API key sent as a bearer token, JSON). Each entry point has its own middleware.
- Web login uses `yiisoft/user`'s `CurrentUser`. Credentials live in `ACCOUNT`, keyed by the employee ID, so the logged-in user's ID is the employee ID. Every web route goes into the route group with the `Authentication` middleware in `config/common/routes.php`, unless it must be public like `/login`.
- Controllers stay thin and call services. Services hold the business rules and depend on repository interfaces. Repositories implement those interfaces with the `yiisoft/db` query builder and return plain entity classes. The web UI calls services directly and never goes through the API.
- Every migration executes its matching file from `SQL/`. The schema is written once, in T-SQL, in those files.
- Roles (admin, manager, employee) and their permissions are RBAC items in `RBAC_ITEM` and `RBAC_ITEM_CHILD`, created by `SQL/008_create_rbac_items.sql` and read by `rbac-db`. Their columns keep the package's lowercase names, the one exception to UPPER_SNAKE. Roles are flat, and permissions are named `<entity>.<action>` (for example `assignment.create`) and mirrored by the `App\Access\Role` and `App\Access\Permission` enums. Admins hold every permission except `assignment.readOwn` (added by `SQL/015`), which only employees hold, because only employees are assigned work; it guards the My assignments page and its calendar. `employee.list` (added by `SQL/016`), which admins and managers hold, guards the Employees list and the work calendar; employees hold `employee.read` only for their own row.
- Each employee's role is stored once, in `EMPLOYEE.ROLE`, with a foreign key that only accepts role names. `ReadOnlyAssignmentsStorage` exposes it to RBAC and refuses writes, and roles change only through the employee service.
- Services check permissions with `AccessChecker::ensure()`, which throws `ForbiddenException`. `AccessChecker` caches each employee's result per permission for its lifetime, which is one request because the container is built per request. Every protected route also gets `->middleware(RequirePermission::for(Permission::X))`, inside the `Authentication` group so guests are redirected to the login page first. Templates hide links and buttons with `access.can('<entity>.<action>')`, and pages add their navbar link to the list in `layout.twig` behind such a check. RBAC says whether a role may do an action at all. `AccessScope` says which rows it may reach (own, subordinates or all), and repositories apply that scope in their queries, returning 404 for rows outside it.
- The outer web route group in `config/common/routes.php` has the `NoStore` middleware, so every web page, `/login` and `/set-password` included, is sent with `Cache-Control: no-store` and actions never set it. Caddy serves `/assets/` with `Cache-Control: public, max-age=31536000, immutable` for 2xx and 304 responses; the asset manager's directory hash changes whenever a file changes.
- Pages render inside the session middleware: `RenderBeforeSessionClose` forces the lazily rendered response, so templates and the layout may read the session (the `flash` view parameter, `currentUser`, `access`). Actions redirect through `Redirector`.
- Services run writes that touch several tables through `TransactionRunnerInterface`. Business-rule errors are a `ValidationException` (field → message), which form actions merge into their field errors with `mergeInto()`. Deletes run through `InUseException::guard()`, which turns a foreign key conflict (SQL Server error 547) into a "still in use" message, and unique writes through `ValidationException::guardUnique()`.
- The web UI is translated with `yiisoft/translator` into English (default), Latvian, Lithuanian, Estonian, Russian, Finnish and Swedish (`en`, `lv`, `lt`, `et`, `ru`, `fi`, `sv`). The English text is the message ID, so there is no English file; the other six live in `messages/<locale>/app.php` (category `app`, ICU formatting through `intl`). `LanguageMiddleware`, right after `ApiPipelineMiddleware`, sets the locale from the `locale` cookie and falls back to English for anything else; `POST /language` sets that cookie (a year, `HttpOnly`, `SameSite=Lax`, `Secure` from the `app/language` param, on in prod) and redirects to a local path only. Templates use `t('...')` with `{name}` parameters, never `|raw`; actions, services and `FlashMessages` translate where they build a message; `yiisoft/validator` uses the `app` category, so every validated property has a `#[Label]`. Stored data (names of employees, sites, work items, access levels) is never translated, dates stay `Y-m-d`, and the API and console stay English.
- Lists are `yiisoft/data` `OffsetPaginator`s over a `QueryDataReader`, with a whitelisted `Sort` built by `ListSort` and the ID as the last tie-break, 20 rows per page. Searching filters the list query through `ListSearch::apply()`, a parameterized `LIKE` over the list's columns combined with `AND` with the scope, and the sort and pagination links keep `q`. The Assignments list also takes the `employee`, `workItem` and `site` filters, combined with the scope; each row's employee, work item and site name links to its filter (`AssignmentList/filter-link.twig`), keeping the sort, `q` and the other filters, and the listing partials keep the view's `filters` in their links. The search form has no button: `instant-search.js` waits 300 ms after typing, fetches the same page with the new `q` (page reset, other parameters such as the filters kept), swaps the list's `data-list-results` container and the `data-list-clear` link, copies the `data-list-status` live-region text and updates the address with `history.replaceState`, so every list template wraps its empty state, table and pagination in `<div data-list-results>`. Without JavaScript, Enter submits the GET form as before.
- Every single `<select>` is enhanced by `assets/select/select.js` into a searchable dropdown: the native select stays in the page, visually hidden, as the posted field and the source of truth, and passes its focus to the new toggle. Lists with more than 8 options get a search box (contains, ignoring case and diacritics) unless the select has `data-select-plain` (the calendar's month and year), and the list is 8 rows high and renders the matches 20 at a time, loading the next 20 as it scrolls. The control follows the select through a `MutationObserver` (options, `hidden`, `disabled`, `class`) and its `change` event, so scripts change the select itself and fire `change` after setting only its value. Selects added to the page later are enhanced on their own. Its texts come from the `data-select-search` and `data-select-no-matches` attributes on `<body>`.
- List rows share one design: text cells go through `truncated-text.twig` (ellipsis at a max width, full text in `title`), empty and no-results texts through `empty-state.twig`, and the row buttons through `row-actions.twig`, in an Actions column (`list-actions`, pinned to the right edge while the table scrolls) that is rendered only when the viewer has a row action. Create, edit, reassign and delete links on the lists carry `data-modal-link`, and every list includes `modal.twig` once. `modal.js` fetches the action's normal page with the `X-Modal: 1` header, shows its `[data-modal-content]` element in a Bootstrap modal with its `[data-modal-title]` heading as the title, closes it on `[data-modal-cancel]`, posts the page's forms with `fetch`, and dispatches a bubbling `app:content-loaded` event on the inserted content, on which page scripts such as `assignment.js` and `employee.js` initialise. `ModalRedirect`, in the outer web route group, answers a redirect to an `X-Modal: 1` request with `204` and `X-Modal-Location`: the script reloads the list when the target is the current page, so its query string and the flash message stay, and otherwise loads the target into the modal. Any other response without modal content becomes a normal page load. Without JavaScript the links open the pages as before.
- "Today" always comes from `Psr\Clock\ClockInterface`, bound to `App\Shared\Clock` in `Europe/Riga` (the `timezone` application param). Queries get dates from PHP as `Y-m-d`, never `GETDATE()`, and dates are shown as `Y-m-d`.
- An assignment (`ASSIGNMENT`, `App\Entity\Assignment`) gives one employee one work item at one construction site for an inclusive `START_DATE` to `END_DATE` period. It has an optional plain-text `DESCRIPTION` (at most 1000 characters, trimmed, empty stored as NULL, shown with `nl2br` after escaping), written on the New and Edit assignment forms and shown in the Work calendar's details. Its stored status is `active`, `done` or `cancelled`; Planned, In progress and Overdue are derived from the dates by `Assignment::displayStatus()`. `WorkItem` is the catalog of possible work, the only "work" term in code.
- An employee needs access to a site during a period (`from` to `to`, both inclusive) when they have an Active assignment there whose period overlaps it and their current access level is at least the site's. `AssignmentRepositoryInterface::findEmployeesNeedingAccess()` is the one query for this; the API reuses it, and a single day is `from = to`.
- `AssignmentService` resolves the actor's scope from their stored role, never from an argument, and loads rows for update and delete through the scoped query, throwing `NotFoundException` (404) for rows outside it.
- An employee's access level is a business rule, not a permission. An employee can be assigned to a site only if their access level is at least the site's required access level, checked whenever an assignment is saved as Active. The assignment service checks this, and an overlapping Active assignment of the same work item at the same site is refused. An Active save runs its checks and write in one transaction that locks the employee row and the site row (`findForUpdate()`, `UPDLOCK`) and then the overlap range (`findOverlappingActive()`, `UPDLOCK, HOLDLOCK`), and a deadlock becomes a "try again" error under Start date. `EmployeeService::update()` locks the employee row the same way before its checks, so a role change and an assignment save of that employee serialize.
- Managers can assign work only to their own subordinates, as defined by the employee's manager reference. `AssignmentService::update()` can change an assignment's employee: the new employee must pass the same assignee rule as a create, and an Active save checks the new employee's level and overlap. An update locks the old and new employee rows in ascending ID order, then the assignment row (`employeeIdForUpdate()`), then the site, then the overlap range. If the assignment's employee is no longer the one the edit form was opened with (the `currentEmployee` hidden field), the save is refused with the "try again" error under Employee, so a stale form or a concurrent reassignment never overwrites another change.
- API keys are issued per external client, stored hashed and revocable individually. They live in `API_KEY` and look like `cwm_<8 hex key ID>_<64 hex secret>`: the key ID is the lookup column and safe to show, only the SHA-256 of the secret is stored, and it is compared with `hash_equals`. Keys are managed only with `./yii api-key:create`, `api-key:list` and `api-key:revoke`, and the plain key is shown once and never logged.
- Failed logins, password setups and API key checks are throttled by `AttemptThrottle`, which counts failures per `ThrottleScope` and key (normalized email or client IP) in `AUTH_THROTTLE`. The table stores only SHA-256 hashes of the keys, one atomic `MERGE` updates it, and every recorded failure deletes the expired rows. The count runs in a fixed window that starts at the first failure. The limits are the `authThrottle` params, read through `ThrottleLimits`. Over the limit, `LoginService` and `PasswordSetupService` still run the dummy hash and throw `TooManyAttemptsException`; the page shows "Too many attempts. Try again in N minutes." with 429 and `Retry-After`. `ApiKeyAuthentication` answers a 429 problem detail. A success clears only the email key. The client IP is `ClientIp::of()`, the request's `REMOTE_ADDR`, because there is no trusted proxy.
- `ApiPipelineMiddleware` is the first entry of the global middleware list. It sends every request whose `urldecode()`d path is `/api` or starts with `/api/` through its own list (`ApiErrorMiddleware`, `ApiKeyAuthentication`, `Router`, with `ApiNotFoundHandler` as fallback), so API routes never get the session, cookies, CSRF, the HTML error pages or `ForbiddenMiddleware`. The rest of the web list stays unchanged. API routes go in the `/api/v1` group in `config/common/routes.php`. The API addresses a construction site by its site code (`CONSTRUCTION_SITE.CODE`, unique, stored trimmed and uppercased, format in `App\Entity\SiteCode`), never by its ID. The optional `from` and `to` query parameters (`YYYY-MM-DD`) give the period, today by default and one day when only one is given; `App\Service\AccessPeriod` validates it (no start before today, at most 12 months), and the response echoes it as `period`.
- Every authentication failure gets the same `401` with `WWW-Authenticate: Bearer`. API responses are JSON from `JsonResponseFactory` with `Cache-Control: no-store`, and errors are RFC 9457 problem details (`application/problem+json`). API clients aren't employees, so API services don't use `AccessChecker`. Any API change updates `docs/openapi.yaml` in the same change: its schemas are strict (`additionalProperties: false`), and `OpenApiDocumentTest` validates real requests and responses against it for every documented status, so an undocumented field or status fails the tests.

## Commands

All commands run inside Docker. Each make target wraps `docker compose`, and each check is a Composer script that CI runs too.

- `make up` / `make down`: start (and install dependencies and apply migrations) / stop the environment. The app is at http://localhost:8080.
- `make migrate`: `./yii migrate:up`, apply pending migrations.
- `make check`: `composer check`, which runs `cs`, `stan`, `test:unit` and `test:integration`.
- `make test`: `composer test`, the unit and integration suites. `test:integration` recreates the test database and applies the migrations first.
- `make composer <args>`, `make shell`: Composer and a shell in the app container.
- `make api-key:create CLIENT="…" [EXPIRES=YYYY-MM-DD]`, `make api-key:list`, `make api-key:revoke ID=<key-id>`: manage API keys.
- `composer cs-fix`: fix code style.

## Conventions

- Every UI string goes into all six `messages/*/app.php` files at the same position. `MessageCatalogTest` fails on a missing, unused or malformed message.
- Text columns are `NVARCHAR` and string literals in SQL use `N'...'`.
- A schema change is a numbered script `SQL/NNN_name.sql`, its rollback `SQL/down/NNN_name.sql`, and a migration class `src/Migration/M<YYMMDDHHMMSS><Name>.php` that extends `SqlFileMigration` and only returns the script name. Each file runs in one transaction. The numbers run without gaps; the next script takes the next number. The scripts were renumbered once to close gaps, so a local database migrated before that must be recreated (`docker compose down -v`, then `make up`).
- In SQL scripts, `GO` separates batches only when it stands alone on a line. Never put a bare `GO` line inside a string or comment, and don't use sqlcmd-only syntax (`GO n`, `:setvar`, `:r`).
- `CREATE DATABASE` and `ALTER DATABASE` never go into `SQL/`. Database creation belongs to the Docker init step.
- Tests are split into a `unit` suite with no database and an `integration` suite that runs against SQL Server. Integration tests that change data run inside a transaction that is rolled back. Tests that change the schema clean up after themselves.
- Code must pass PHP-CS-Fixer and PHPStan before it is committed.

## Workflow

- `main` is the default branch and is protected: changes reach it only through a pull request with passing checks.
- Features are built on `feature/<spec-name>` and fixes on `fix/<spec-name>`, where `<spec-name>` is the spec's filename without `.spec.md`.
- Order of work: create the branch from `origin/main`, write the spec on it as the first commit, then implement. The spec and its implementation reach `main` in the same pull request.

## Specs

- Specs live in `specs/shared/` and are committed. They stay there after their pull request is merged and are frozen from then on: a later change to a feature gets its own new spec instead of editing the old one. `specs/personal/` is gitignored and only used when asked.
- Read a feature's spec before implementing it.
